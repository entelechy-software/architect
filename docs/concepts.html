Core Concepts

Architect is built around three composable layers: Builders, Definitions, and Engines. Understanding this model will make every other part of the docs click.

The Three Layers

1. Builder — fluent configuration API

Builders are PHP objects with a fluent API you chain to describe your UI. They validate configuration at definition time (not at render time), so mistakes surface during development rather than in production.

// A builder call:
$definition = ArchitectTableDefinition::make()
    ->title('Members')
    ->dataModel(MemberDataModel::class)
    ->columns([
        TextColumn::make('name')->sortable(),
    ]);

2. Definition — serialisable value object

Calling ->build() (or, on table definitions, ->definition()) returns a plain value object — a Definition. Definitions hold no behaviour; they are data. This makes them safe to cache, pass to Livewire, and hand to rendering engines.

// Definition classes act as both builder and value object:
class MembersTableDefinition extends ArchitectTableDefinition
{
    public function definition(): static
    {
        return $this->title('Members')->columns([...]);
    }
}

3. Engine — Livewire rendering component

Engines are Livewire components that consume a Definition and render the final HTML. You never instantiate an Engine directly — pass a Definition (or definition class name) to the <x-architect> Blade component:

<!-- Pass an instantiated definition: -->
<x-architect :definition="$definition" />

<!-- Pass the FQCN string (the component instantiates it): -->
<x-architect definition-class="\App\Modules\Members\Tables\MembersTableDefinition" />

The Architect Facade

The Architect facade is the single entry point for starting any builder chain. It returns the correct builder type for the requested subsystem:

use Entelechy\Architect\Facades\Architect;

Architect::make('table')     // → ArchitectTableDefinition builder
Architect::tabs()            // → ArchitectNavigatorDefinition builder (pill tabs)
Architect::workspaceTabs()   // → WorkspaceTabsDefinition builder
Architect::dashboard()       // → DashboardBuilder
Architect::form()            // → FormBuilder
Architect::content()         // → ContentBuilder
Architect::toolbar()         // → ToolbarBuilder
Architect::supersearch()     // → SupersearchDefinition builder
Architect::toast()           // → NotificationBuilder (type: toast)
Architect::alert()           // → NotificationBuilder (type: alert)
Architect::notify($user)     // → NotificationBuilder (type: inbox, for user)
Architect::announce()        // → NotificationBuilder (type: announcement)

DataModel — the ORM bridge

Architect doesn't tie directly to Eloquent models. Instead, you create a DataModel class that acts as an adapter. This keeps your domain models clean and gives Architect full control over query optimisation.

use Entelechy\Architect\Tables\DataModel;

class MemberDataModel extends DataModel
{
    protected string $model = Member::class;
    protected string $table = 'members';

    public function getQuery(): Builder
    {
        return Member::query()->withTrashed();
    }
}

The TableEngine calls getQuery() and applies all column filters, sorts, and searches on top of it.

Module Structure

Architect is designed for modular monolith codebases. Each feature lives in its own module directory:

app/Modules/Members/
├── Components/
│   ├── Tables/
│   │   └── MembersTableDefinition.php
│   ├── Navigators/
│   │   └── MembersNavigator.php
│   └── Tabs/
│       └── MembersTabsDefinition.php
├── Models/
│   ├── Member.php              ← domain model
│   └── MemberDataModel.php    ← Architect adapter
├── Routes/
│   └── web.php
├── Views/
│   └── index.blade.php
├── database/
│   └── migrations/
└── MembersServiceProvider.php
Cross-module isolation Modules must NOT import each other's Eloquent models. Cross-module data access should go through an API or service layer. Architect definitions live in Components/ and are private to their module.

Rendering Pipeline

When <x-architect :definition="$definition" /> is evaluated:

  1. The Architect Blade component reads the type property of the definition.
  2. It mounts the correct Livewire engine component with the definition as a constructor property.
  3. The engine calls getQuery() on the data model (for tables) or resolves values (for dashboards).
  4. Livewire renders the engine's Blade template. Alpine.js powers client-side interactivity.
  5. Subsequent interactions (sort, search, paginate, open modal) trigger Livewire method calls, which re-render only the relevant component.

Authorization

Architect integrates with your application's authorization layer via a permission() call on any builder. Pass a permission node string or a closure:

TextColumn::make('salary')
    ->label('Salary')
    ->permission('hr.view_salary');

// Or as a closure (receives the authenticated user):
TextColumn::make('salary')
    ->permission(fn ($user) => $user->hasRole('hr'));

Permission nodes are passed to Laravel's Gate::check() by default. This is configurable in config/architect.php.
