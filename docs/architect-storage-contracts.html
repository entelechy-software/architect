Core Subsystems

Storage Contracts

Named, reusable retention policies that describe how long records and uploaded files live at each stage of their lifecycle before being permanently destroyed.

Destructive and opt-in Cold Storage and Purge are one-way transitions with no restore path. Both storage_contracts.enabled and file_retention.enabled default to false — this feature must be deliberately configured via php artisan architect:storage:init.

The Four DB Record Stages

Every record under a storage contract passes through four stages:

StageWhat happensRestorable?
ArchivedExisting Laravel SoftDeletes (deleted_at) — unchanged behaviour. This is what ->archivable() / BulkArchiveAction already do in the Table module.Yes
RetiredA further time-based marker stage after Archived. No data movement yet, just a ledger flag/timestamp.Yes
Cold StorageThe row (+ declared relations) is serialized to JSON and written to a Laravel filesystem disk, then the DB row is hard-deleted.No
PurgedThe cold storage file itself is deleted. A minimal ledger row (model type/id/contract/timestamps only, no data) survives as a historical record.No

Each named contract configures its own duration for all three transitions. A contract's cold_storage duration left null/absent means "never auto-purge" for that contract — the record stays in Cold Storage indefinitely.

Configuration

// config/architect.php — written by `php artisan architect:storage:init`, don't hand-edit `contracts`.
'storage_contracts' => [
    'enabled' => true,
    'cold_disk' => 'glacier',           // any disk from config/filesystems.php
    'default_contract' => 'standard',
    'contracts' => [
        'standard' => ['archived' => '2 years', 'retired' => '1 year', 'cold_storage' => '1 year'],
        'finance'  => ['archived' => '6 years', 'retired' => '2 years', 'cold_storage' => '1 year'],
    ],
    'ledger' => [
        'connection' => null,           // null = config('database.default')
        'table' => 'architect_storage_ledger',
    ],
    'reference_doc' => ['enabled' => true],
    'discovery' => [
        'paths' => [],                  // required — see "Discovery" below
    ],
],

Assigning a Contract to a Model

Use the HasStorageContract trait, assigned via a fluent static call inside the model's own booted() hook — not a property, not a central registry. Models using this trait must also use SoftDeletes, since the Archived stage is deleted_at.

use Illuminate\Database\Eloquent\Model;
use Illuminate\Database\Eloquent\SoftDeletes;
use Entelechy\Architect\Concerns\HasStorageContract;

class Invoice extends Model
{
    use SoftDeletes, HasStorageContract;

    protected static function booted(): void
    {
        static::storageContract('finance');
    }
}

A model that uses the trait but never calls static::storageContract() silently falls back to whichever contract is flagged default_contract. Ledger bookkeeping happens automatically: soft-deleting the model creates an architect_storage_ledger row at the Archived stage; restoring it before Cold Storage removes that row again.

Commands

CommandPurpose
architect:storage:initFully interactive: define contracts and their durations, pick the default, choose the ledger table/connection, opt in to File Retention, and opt in to generating the reference doc. Re-running loads existing contracts and lets you add/edit/remove them — it never blindly overwrites.
architect:storage:discoverScans the definition classes under storage_contracts.discovery.paths for file-upload columns (Column::make('path')->type('upload')) and reports which models use HasStorageContract. Writes an informational, non-authoritative cache into config — the model's own booted() call remains the source of truth at runtime.
architect:storage:sweepThe daily job that advances every record/file through its lifecycle by one stage once the relevant duration has elapsed. Auto-registered on Laravel's scheduler — your app only needs its normal schedule:run cron.
Discovery paths are required, not inferred storage_contracts.discovery.paths has no default value. architect:storage:discover fails fast with a clear error if it's empty — set it explicitly to the directories containing your *Definition classes (e.g. app/Modules/**/Components/Tables).

Cold Storage is Disk-Agnostic

Both the Cold Storage transition and File Retention's soft-delete/purge actions operate purely through Laravel's Storage facade — never a provider-specific SDK call. Point cold_disk at any driver configured in config/filesystems.php (S3 with a Glacier storage class, another S3-compatible service, GCS, local, etc.) and it works with zero package-specific code.

The transition itself is write → verify → force-delete, never delete-before-confirmed-write: the row is serialized to JSON and written to the cold disk, existence is verified, and only then is the database row hard-deleted.

// Optional extension point: declare relations to include in the cold-storage snapshot.
class Invoice extends Model
{
    use SoftDeletes, HasStorageContract;

    public function coldStorageRelations(): array
    {
        return ['lineItems', 'customer'];
    }
}

File Retention (Uploaded/Attached Files)

Distinct from the four-stage DB record lifecycle above — files are tracked by last-accessed time, not by how long a parent record has existed, using a simpler two-stage lifecycle:

StageTrigger
Active → Soft-deletedThe file hasn't been accessed for the contract's inactive duration.
Soft-deleted → Permanently removedA further purge duration elapses with no access. There is no Cold Storage stage for files — straight to permanently removed.
 
'file_retention' => [
    'enabled' => true,
    'default_contract' => 'standard-files',
    'contracts' => [
        'standard-files'  => ['inactive' => '1 year', 'purge' => '6 months'],
        'sensitive-files' => ['inactive' => '90 days', 'purge' => '30 days'],
    ],
    'ledger' => [
        'connection' => null,
        'table' => 'architect_uploads',
    ],
],

Standalone/Orphan Uploads

Files not tied to any Eloquent model are tracked in the architect_uploads ledger, populated explicitly by your app at upload time via the Architect facade:

use Entelechy\Architect\Architect;

Architect::trackUpload($path, disk: 'uploads', contract: 'sensitive-files');
// contract is optional — falls back to file_retention.default_contract
v1 limitation: model-attached files are not yet swept architect:storage:sweep's file-retention phases currently only sweep the standalone architect_uploads ledger (files registered via Architect::trackUpload()). Columns declared via HasStorageContract::fileRetentionContract() on a model are discoverable (see architect:storage:discover) but not yet swept — that requires last_accessed_at tracking through a package file-serving path, which is not implemented in this release. Track access explicitly via Architect::trackUpload() in the meantime for anything you want auto-purged.

Regardless of category, last_accessed_at is only updated when a file is served through the package's file-serving path. Files served directly by a CDN or reverse proxy that bypasses Laravel won't have their access time updated — a known limitation, not solved automatically in v1.

Reference Doc

When storage_contracts.reference_doc.enabled is true, architect:storage:init generates a static, self-contained HTML summary at docs/storage-contracts.html (relative to your app's base path, not configurable) — regenerated on every subsequent run. It's written in plain language for three audiences: the project developer, legal/commercial teams drafting a retention policy, and end users as a transparency page that can be published on your site.

Safety Notes

  • Cold storage transition is write → verify → force-delete per record, never delete-before-confirmed-write.
  • Purge is irreversible. Both storage_contracts.enabled and file_retention.enabled default to false.
  • A contract's cold_storage (or purge, for files) duration being null/absent is an explicit, deliberate "never auto-purge" setting — not an oversight.
  • Exactly one contract must be flagged as each feature's default_contract — validated at write-time by architect:storage:init.
  • Per-tenant retention overrides are not supported — retention policy is system-wide, even in multi-tenant hosts (the ledger's own table/connection can still be pinned to a central/landlord connection during setup).
